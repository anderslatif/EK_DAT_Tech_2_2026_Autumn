# Hash Functions

A hash function is a function that takes an input and returns a fixed-size string.

The hash value is also called a "digest" because it can boil down a large input to a small representation.

Hash functions are **one-way functions**, meaning that it is easy to compute the hash from the input, but computationally hard to go from the hash back to the input.

A small change in the input will produce a completely different output. This is called the avalanche effect.

Try to run these two commands:

```bash
echo -n "org.springframework:spring-core:6.1.0" | git hash-object --stdin
echo -n "org.springframework:spring-core:6.1.1" | git hash-object --stdin
```

It remains true for much larger inputs (when hashing files).

# Caching Maven Dependencies

Caching dependencies speeds up our workflow execution time.

Instead of downloading the dependencies every time the workflow runs, we can retrieve them from a cache in GitHub Actions.

In GitHub Actions this requires a single request (compressed tarball) instead of hundreds of sequential-ish requests to Maven Central.

In a big company it could amount to hundreds of minutes a month per workflow!

* (+) Do it to save time.

* (+) Do it to save money.

* (+) Do it for the environment!

---

# Caching Maven Dependencies - Example


```yaml
name: Java CI

on:
  push:
    branches:
      - main
  pull_request:
    branches:
      - main

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - name: Set up JDK
        uses: actions/setup-java@v4
        with:
          java-version: "21"
          distribution: "temurin"
      - name: Cache Maven dependencies
        uses: actions/cache@v4
        with:
          path: ~/.m2/repository
          key: ${{ runner.os }}-maven-${{ hashFiles('**/pom.xml') }}
          restore-keys: ${{ runner.os }}-maven-
      - name: Run tests
        run: mvn test
```

---

# Caching Maven Dependencies - Explanation

`.m2` is where Maven stores its dependencies.

The `pom.xml` file is hashed and the key is used to tell if the cache is still valid.

If the tiniest change occurs to the file, the hash will be new and the cache will be invalidated (meaning that it will re-download the dependencies).

*What if there are changes to the `pom.xml` file that do not affect the dependencies?*

The cache will still be invalidated, even if we doesn't need to. That approach is said to be [heurestic](https://en.wikipedia.org/wiki/Heuristic) (not optimized but "*good enough*").

# Real World Supply Chain Attack Example

March, 2025. `tj-actions/changed-files` was compromised by a malicious actor who gained access to the account of a maintainer. 

The hacker published a new version of the action that would send secrets from GitHub Actions workflows to a remote server.

The malicious code would read the memory, scan it for secret tokens, base64 encode them and dump them to the build logs.

Anyone that included the (at the time) latest version of the 3rd party action in their workflow were compromised when running their workflow.

Further reading for the curious: [1](https://www.wiz.io/blog/github-action-tj-actions-changed-files-supply-chain-attack-cve-2025-30066) [2](https://www.oasis.security/blog/tj-actions) [3](https://www.stepsecurity.io/blog/harden-runner-detection-tj-actions-changed-files-action-is-compromised).

# Versioning

Could the solution to supply chain attack be to add a version?

```yaml
- name: Set up JDK
  uses: actions/setup-java@v3
```

**No!**

A version tag is just a label that can be moved to point to a different commit. The hacker could still move the tag to point to their malicious commit.

Instead, we want to point to the commit. We do this by pinning it to the commit hash.

**Hash pinning** is now a recommended [security hardening practice](https://docs.github.com/en/actions/reference/security/secure-use) by GitHub.

---

# How to do it

Without hash-pinning:

```yaml
- name: Set up JDK
  uses: actions/setup-java@v3
```

With hash-pinning:

```yaml
- name: Set up JDK
  uses: actions/setup-java@03ad4de0992f5dab5e18fcb136590ce7c4a0ac95 # v5.6.0, 2026-06-16
```

Adding comments with version and date is a good practice to inform the reader.

Often the date is ommited but without it, it isn't evident how out of date the pin is. Hash pinning is not a set and forget practice. It is up to the developer to update the pin with new versions as older versions might have security vulnerabilities.

---

# What to look for

1. Use published releases of the action rather than unversioned commits.

2. Prefer Actions published under `/actions` (GitHub's official Actions) or GitHub verified creators (blue checkmark).

3. Don't always go for the latest version. Wait a few weeks to let problems surface and be fixed.

4. Get the commit hash from GitHub. Don't get it from online tutorials or LLM's.

# Exercise - Find the latest hash pin

1. Go to: https://github.com/actions/setup-java

2. Find the **Releases** section on the right side and click on the latest release.

3. Note the **Version number**, **Published date**, and **Commit hash**.

4. Add the hash pin to your workflow file, along with a comment containing the version number and published date.

The format is:

```yaml
- name: Set up JDK
  uses: actions/setup-java@<commit-hash> # <version-number>, <published-date>
```
